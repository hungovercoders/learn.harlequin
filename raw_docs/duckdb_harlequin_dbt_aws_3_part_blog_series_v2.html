Part 1 — DuckDB + Harlequin: Delightful Local Data Engineering

Story: begin with the smallest useful stack. No dbt and no cloud. Generate representative events, query Parquet directly with DuckDB, turn useful queries into a tiny SQL pipeline, and use Harlequin as the interactive workbench.

1. Setup with uv

uv init
uv python pin 3.12
uv add duckdb pandas pyarrow faker harlequin

Why no analytics.duckdb yet? In Part 1, Parquet is the durable storage layer and DuckDB is the query/compute engine. DuckDB can query Parquet directly, so a persistent database file is unnecessary. We introduce analytics.duckdb in Part 2, when dbt needs a durable catalog for stable views and other managed relations.

2. Parquet is storage; DuckDB is the engine

A DuckDB database file is optional. This query reads Parquet directly without importing it:

select * from read_parquet('data/raw/events/*.parquet');
PART 1 data/raw/events/*.parquet │ ▼ DuckDB query / transform │ ├──────────► Harlequin ▼ data/clean/events.parquet │ ▼ data/summary/daily_events.parquet Durable data = Parquet Compute/query engine = DuckDB Interactive UI = Harlequin

A persistent analytics.duckdb becomes useful when DuckDB itself should retain schemas, tables, views and catalog metadata between sessions. A table created in DuckDB stores its result in that database file; a view can retain only its query definition while continuing to read external Parquet. Part 1 deliberately stays file-first.

3. Generate fake events

from pathlib import Path
from datetime import datetime, timedelta, timezone
import random, uuid
import pandas as pd
from faker import Faker

fake = Faker()
random.seed(42)
Faker.seed(42)

out = Path("data/raw/events")
out.mkdir(parents=True, exist_ok=True)

types = ["page_view","search","product_view","add_to_cart",
         "checkout_started","purchase"]
devices = ["web","ios","android"]
customers = [f"cust_{i:05d}" for i in range(2000)]
end = datetime.now(timezone.utc)
start = end - timedelta(days=30)
rows = []

for _ in range(50_000):
    event_type = random.choices(types, weights=[40,10,22,12,8,8], k=1)[0]
    rows.append({
        "event_id": str(uuid.uuid4()),
        "event_timestamp": start + timedelta(
            seconds=random.randint(0, int((end-start).total_seconds()))
        ),
        "customer_id": random.choice(customers),
        "session_id": str(uuid.uuid4()),
        "event_type": event_type,
        "device": random.choice(devices),
        "country": fake.country_code(),
        "revenue": round(random.uniform(5,250),2)
                   if event_type == "purchase" else 0.0,
    })

df = pd.DataFrame(rows)
df["day"] = pd.to_datetime(df["event_timestamp"]).dt.date
for day, frame in df.groupby("day"):
    frame.drop(columns=["day"]).to_parquet(
        out / f"events_{day}.parquet", index=False
    )
uv run python scripts/generate_fake_events.py

6. A deliberately simple pipeline

sql/01_clean_events.sql writes clean Parquet rather than importing the result into a DuckDB database:

COPY (
  select
    event_id,
    cast(event_timestamp as timestamp) as event_timestamp,
    cast(event_timestamp as date) as event_date,
    customer_id, session_id,
    lower(event_type) as event_type,
    lower(device) as device,
    upper(country) as country,
    cast(revenue as double) as revenue
  from read_parquet('data/raw/events/*.parquet')
  where event_id is not null and customer_id is not null
)
TO 'data/clean/events.parquet' (FORMAT PARQUET);

sql/02_daily_summary.sql reads that file and creates the summary data product:

COPY (
  select
    event_date, event_type, device, country,
    count(*) as event_count,
    count(distinct customer_id) as unique_customers,
    count(distinct session_id) as unique_sessions,
    sum(revenue) as revenue
  from read_parquet('data/clean/events.parquet')
  group by 1,2,3,4
)
TO 'data/summary/daily_events.parquet' (FORMAT PARQUET);

scripts/run_pipeline.py:

from pathlib import Path
import duckdb

with duckdb.connect(":memory:") as con:
    for file in ["sql/01_clean_events.sql", "sql/02_daily_summary.sql"]:
        con.execute(Path(file).read_text())
uv run python scripts/run_pipeline.py

Part 1 hand-off: the stack is intentionally tiny and pleasant. As models multiply, however, the custom runner lacks a dependency graph, model tests and a clean environment boundary. Those are the reasons—not fashion—to introduce dbt in Part 2.

Part 2 — Add dbt: Pipeline Rigour and Environment Awareness

Story: preserve the local DuckDB/Harlequin experience while replacing the hand-written runner with dbt. Most importantly, put physical location behind a stable dbt source so downstream SQL is environment-agnostic from day one.

1. Add dbt-duckdb

uv add dbt-duckdb

├── staging/

dbt_project.yml

2. Now analytics.duckdb has a purpose

Part 1 used DuckDB without a persistent database. With dbt, a persistent DuckDB catalog becomes useful because dbt creates named relations that should survive between sessions. We introduce analytics.duckdb here.

data/raw/events/*.parquet │ ▼ analytics.duckdb ┌───────────────────────────────┐ │ catalog + schemas │ │ stg_events VIEW │ │ fct_daily_event_summary VIEW │ │ future tables/incrementals │ └───────────────────────────────┘ ▲ dbt

The database file does not have to contain the raw rows. A dbt-created view can live in analytics.duckdb while its definition reads external Parquet. The file is now the persistent catalog/relation layer; Parquet can remain the physical data layer.

A view over external Parquet does not copy the rows into analytics.duckdb; the files must still exist when queried. A dbt table materialization is different: its result is persisted into the DuckDB database.

3. Configure local DuckDB

dbt_project.yml:

name: analytics_engineering
version: "1.0.0"
config-version: 2
profile: analytics_engineering
model-paths: ["models"]

models:
  analytics_engineering:
    staging:
      +materialized: view
    marts:
      +materialized: view

profiles.yml:

analytics_engineering:
  target: "{{ env_var('DBT_TARGET', 'local') }}"
  outputs:
    local:
      type: duckdb
      path: analytics.duckdb
      schema: analytics
      threads: 4
      extensions:
        - parquet

4. Stable source name, dynamic physical location

models/sources/raw_sources.yml:

version: 2

sources:
  - name: raw
    tables:
      - name: events
        config:
          external_location: "{{ env_var(
            'EVENTS_LOCATION',
            'data/raw/events/*.parquet'
          ) }}"
EVENTS_LOCATION ↓ source('raw','events') ← stable logical contract ↓ stg_events ← stable view ↓ fct_daily_event_summary ← stable mart Today: data/raw/events/*.parquet Later: s3://bucket/raw/events/*.parquet
Do not create events_local and events_s3. Keep infrastructure out of model names. Only the source boundary should know the physical location.

5. dbt creates the stable views

models/staging/stg_events.sql:

{{ config(materialized='view') }}

select
  event_id,
  cast(event_timestamp as timestamp) as event_timestamp,
  cast(event_timestamp as date) as event_date,
  customer_id, session_id,
  lower(event_type) as event_type,
  lower(device) as device,
  upper(country) as country,
  cast(revenue as double) as revenue
from {{ source('raw','events') }}
where event_id is not null and customer_id is not null

models/marts/fct_daily_event_summary.sql:

{{ config(materialized='view') }}

select
  event_date, event_type, device, country,
  count(*) as event_count,
  count(distinct customer_id) as unique_customers,
  count(distinct session_id) as unique_sessions,
  sum(revenue) as revenue
from {{ ref('stg_events') }}
group by 1,2,3,4

8. Views, tables, incremental and external models

TypeWhen to use it
viewGreat default for staging and lightweight marts.
tablePersist expensive results or snapshots.
incrementalPersisted models are too large to rebuild fully.
externalThe output contract should itself be Parquet/CSV/JSON.

9. DuckDB extension lifecycle and .duckdbrc

.duckdbrc is DuckDB startup SQL, not Harlequin configuration. Use it for runtime setup in clients that honour it:

LOAD parquet;
LOAD httpfs;
LOAD aws;

Install separately during environment bootstrap:

import duckdb

with duckdb.connect("analytics.duckdb") as con:
    con.execute("INSTALL parquet")
    con.execute("INSTALL httpfs")
    con.execute("INSTALL aws")
bootstrap: INSTALL extension → runtime: LOAD extension

dbt-duckdb can also manage required extensions for its own connections from the dbt profile.

Part 2 hand-off: everything still works locally, but the project is already cloud-ready. The physical location is behind the dbt source contract. Part 3 should therefore be boring in the best possible way: add AWS authentication and an S3 target, change configuration, and run the same DAG.

Part 3 — Deploy the Same Pipeline to AWS

Story: cash in on the abstraction from Part 2. AWS supplies storage, identity and a runtime; it does not require a second version of the data pipeline.

1. The transition

LOCAL AWS data/raw/events/*.parquet s3://bucket/raw/events/*.parquet \ / \ / source('raw','events') ↓ stg_events ↓ fct_daily_event_summary ↓ same dbt build

2. Add an S3-capable target

analytics_engineering:
  target: "{{ env_var('DBT_TARGET', 'local') }}"
  outputs:
    local:
      type: duckdb
      path: analytics.duckdb
      schema: analytics
      threads: 4
      extensions: [parquet]

    s3:
      type: duckdb
      path: analytics.duckdb
      schema: analytics
      threads: 4
      extensions:
        - parquet
        - httpfs
        - aws
      secrets:
        - type: s3
          provider: credential_chain
          region: "{{ env_var('AWS_REGION', 'eu-west-2') }}"

3. Authenticate and switch configuration

aws sso login --profile analytics

export AWS_PROFILE=analytics
export AWS_REGION=eu-west-2
export DBT_PROFILES_DIR="$(pwd)"
export DBT_TARGET=s3
export EVENTS_LOCATION="s3://my-data-platform/raw/events/*.parquet"

uv run dbt debug
uv run dbt build
No staging or mart SQL changes. That is the payoff of putting environment differences at the boundary in Part 2.

4. Make outputs dynamic too

{{

5. AWS IAM: least privilege

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["s3:ListBucket"],
      "Resource": "arn:aws:s3:::my-data-platform",
      "Condition": {
        "StringLike": {"s3:prefix": ["raw/events/*"]}
      }
    },
    {
      "Effect": "Allow",
      "Action": ["s3:GetObject"],
      "Resource": "arn:aws:s3:::my-data-platform/raw/events/*"
    },
    {
      "Effect": "Allow",
      "Action": ["s3:PutObject"],
      "Resource": "arn:aws:s3:::my-data-platform/summary/*"
    }
  ]
}
Never commit AWS keys to SQL, profiles.yml, .duckdbrc, Docker images or Git. Use SSO for humans and IAM roles/OIDC/temporary credentials for deployed workloads.

6. Deploy a job, not a database server

DuckDB is embedded. The production unit can be a container/job whose meaningful application command is simply:

uv sync --frozen
uv run dbt build

A minimal uv-based image:

FROM python:3.12-slim
WORKDIR /app
RUN pip install --no-cache-dir uv
COPY pyproject.toml uv.lock ./
RUN uv sync --frozen
COPY . .
CMD ["uv", "run", "dbt", "build"]

Run that image using your organisation's existing AWS job/container platform and attach an IAM role rather than developer credentials.

7. Keep the developer tools

Harlequin remains useful for authenticated investigation of the resulting DuckDB views; hsql remains useful for small operational smoke checks.

uv run hsql analytics.duckdb \
  -c "select max(event_date) from analytics.fct_daily_event_summary;"

uv run harlequin --theme dracula analytics.duckdb

8. Final architecture

uv │ ├── DuckDB engine ├── dbt DAG + tests + environment contracts ├── Harlequin interactive development └── hsql headless checks │ ▼ source('raw','events') │ ┌─────┴─────┐ ▼ ▼ local AWS S3 Parquet Parquet └─────┬─────┘ ▼ stable models ▼ local or S3 outputs

9. Series takeaway

PartWhat we addWhy
1DuckDB + Parquet + HarlequinFast, enjoyable local development.
2dbtTests, dependencies, lineage and environment abstraction.
3AWS S3 + IAM + runtimeCloud storage and execution without rewriting the pipeline.
Core principle: make local development excellent first, add pipeline structure when it solves a real problem, and make cloud deployment a configuration change rather than an architectural rewrite.
